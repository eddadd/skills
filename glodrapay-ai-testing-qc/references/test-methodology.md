# 测试方法论：从产出物到断言，从断言到证据

本文档回答两个核心问题：**怎么把验收标准转成靠谱的测试**、**怎么判断 AI 生成的测试靠不靠谱**。

---

## 一、验收标准 → 断言清单（消费 openspec 产出物）

### 1.1 提取规则

从 `tasks.md` 提取全部「验收标准：」条目，登记成表：

| 列 | 说明 | 示例 |
| --- | --- | --- |
| 编号 | 断言唯一号 | A-01 |
| 断言内容 | 验收标准原文（保持中文） | 点击导出后 exportUserServer 恰调用 1 次 |
| 来源 | 任务号 + spec 场景号 | T3.2 / spec S5 |
| 类型 | 请求 / 显隐 / 文案 / 行为 / 数据 | 请求 |
| 验证方式 | network / DOM / 走查 / 单测 | network |

### 1.2 断言类型 → 验证手段映射

| 断言类型 | 主手段 | 兜底手段 |
| --- | --- | --- |
| 请求次数 / 入参 | chrome-devtools `list_network_requests` + `get_network_request` 对比请求体 | 代码走查（标注为静态证据） |
| 权限显隐 / 空态 / loading | `evaluate_script` 读 DOM 存在性、computed style | 截图（接口超时不强求） |
| 文案 / i18n | 切语言后 `evaluate_script` 读文本 | 走查 locales 文件 key 存在性 |
| 数据转换 / 纯函数 | 单测（可选层） | 走查 |
| 跨模块契约（路由注册、枚举分支） | 走查 + 全仓检索符号 | — |

### 1.3 对照互补检查（与 spec 的交叉验证）

- spec 有 `#### 场景` 但断言清单无对应条目 → **缺口**，补断言；
- tasks 有验收标准但 spec 无场景支撑 → **存疑**，向用户核对来源，不擅自测。

## 二、测试用例生成套路（防快乐路径）

### 2.1 每条正向断言必问四个反向问题

1. **不触发会怎样**？（没权限、没数据、没点击）
2. **触发两次会怎样**？（防重、防重复请求）
3. **输入坏了会怎样**？（空值 / 非法枚举 / 超长）
4. **环境坏了会怎样**？（接口失败 / 超时 / 数据缺失）

四个问题里有答案的，都展开成独立反向用例——这就是把「1 条验收标准」扩成「1 正 + N 反」的方法。

### 2.2 用例数量 sanity check

- 单模块少于 8 条用例 → 大概率只测了快乐路径，回 2.1 重问；
- 反向用例占比 < 40% → 边界覆盖不足，回 2.1 重问；
- 参考基准：add-payment-audit 实战产出 23 条（业务 17 + 代码 6），覆盖空态 / 越权显隐 / 重置 / 语言切换 / 提交拦截。

### 2.3 mock 注入决策树

```
测试数据不全？
├─ 项目用 fetch → 请求拦截
├─ 项目用 axios/XHR（大多数后台项目）→ initScript 包裹 XMLHttpRequest.prototype
│   重写 readystatechange → 改 responseText → 注入目标状态
└─ 数据可从 UI 构造（表单提交等）→ 不 mock，真实构造
```

要点：initScript 在 navigate 时注入，刷新后仍生效；mock 只改**响应数据**，不改被测行为本身。

## 三、AI 生成测试的靠谱性判断（五条硬标准）

测试产出后逐条自检，不过关的用例**删掉重写**，不带病交付：

1. **可证伪**：每条断言能明确说出「怎样算失败」。「页面正常」不可证伪 → 改成「按钮不渲染且无 console 报错」。
2. **正反都有**：至少一半用例覆盖「不应该发生」的行为（越权仍显示、重复请求、失败崩溃）。
3. **不依赖实现细节**：断言绑外部可观察行为（请求次数、DOM、文案），不绑函数名 / switch 写法——实现重构不该导致断言失效。
4. **mock 不越界**：mock 替代的是「不可控外部依赖」（后端数据、第三方），禁止 mock 被测行为本身（被测函数内部逻辑、被测组件的渲染）。
5. **变异抽查**：对最关键的 1-2 条断言做变异验证——临时把代码改坏（如 `===` 改 `!==`、`v-if` 取反），跑测试确认**能抓住**，再还原。抓不住的断言是假断言。

### 3.1 变异验证操作规程

- 前置条件：工作区改动少 → 直接变异；改动多 → **先临时 commit 到分支再变异**，测完 revert，**禁止 git stash**（会与未提交改动冲突）。
- 变异点选择：挑断言直接依赖的那行代码（显隐条件、请求参数拼装）。
- 还原后必须 `rg` 确认变异串 0 残留。

## 四、证据与报告纪律

- 每条「通过」都要有证据：网络请求摘录、DOM/computed style 输出、单测运行结果。
- 截图接口超时 → 不重试，改 `evaluate_script` 读 computed style / DOM 结构，证据反而更精确。
- 「无法验证」是合法结论：需真实联调的链路（后端就绪、真实支付流）如实标注，禁止宣称全覆盖。
- 报告里区分三档结论：通过 / 失败（附证据与修复）/ 无法验证（附原因）。
