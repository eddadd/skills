# AI 测试质检（glodrapay-ai-testing-qc）

## 定位与边界

本 skill 是**测试执行者与质检员**：把「验收标准 / spec 场景 / 需求描述」转成可执行的测试，跑完给出分级报告，发现问题当场修复并回归。它不负责写业务代码（除测试发现的 bug 修复）、不改 openspec 产出物。

与 `openspec-spec-methodology` 的协作契约（下游消费方视角）：

1. **优先消费 tasks.md 的「验收标准」条目**——该 skill 已保证验收标准「可转断言、独立成条目、不依赖实现细节」，本 skill 逐条把它转成测试用例。
2. **对照 spec.md 的 `#### 场景` 互补**——验收标准约束「如何验证」，spec 场景约束「行为是什么」；两边对照查缺：spec 有场景但 tasks 无对应验收 → 提示补验收；tasks 有验收但 spec 无场景 → 提示核对来源。
3. **无 openspec 产出物时降级**——从用户需求描述或既有代码出发走查，报告中标注「无 spec 依据，为探索性测试」。

## 触发方式

- **显式触发**：用户说「测试」「质检」「查 bug」「跑测试」「自查」「验证一下」等。
- **apply 后提示**：检测到 `/opsx-apply` 工作流刚完成（产出物 tasks 全部 done）时，主动问一句「产出物已就绪，是否对本变更跑测试质检？」——不自动开跑，等用户确认。

## 执行流程（四步）

### 第一步：测试输入准备（消费产出物）

1. 定位测试对象：openspec change 目录（`openspec/changes/<name>/`）或用户指定的模块。
2. 读取并整理测试输入，产出**断言清单**：
   - 从 `tasks.md` 提取全部「验收标准：」条目 → 每条登记：`编号 / 断言内容 / 来源任务号 / 可自动化方式`；
   - 从 `specs/*/spec.md` 提取 `#### 场景` → 与断言清单对照标注覆盖关系；
   - 无产出物时：从需求描述提炼「应该发生 / 不应该发生」清单。
3. 向用户确认测试范围（全量 / 抽查 / 只测新增）与环境（dev 地址、是否需要 mock 数据）。

### 第二步：业务行为层测试（浏览器实测）

逐条执行断言清单，优先真实数据，数据不全时用 mock 兜底：

- **请求断言**：通过 chrome-devtools `list_network_requests` / `get_network_request` 验证「调用次数、入参内容（不含分页、携带筛选）」，对应验收标准里的请求类断言。
- **显隐断言**：`evaluate_script` 读 DOM / computed style，验证权限显隐、空态、loading、文案（含 i18n 双语言切换）。
- **XHR mock 兜底**（测试数据不全时）：fetch 拦截对 axios/XHR 项目无效；用 `navigate_page` 的 `initScript` 包裹 `XMLHttpRequest.prototype`，重写 `readystatechange` 的 `responseText` 注入目标状态数据（如 PENDING）。initScript 在导航时注入，刷新后仍生效。
- **正反对照**：同一页面构造正反数据（如「有权限的行显示按钮、无权限的行不显示」），比单场景断言更有说服力。
- 每条断言记录：通过 / 失败 / 无法验证（标注原因，如「需真实联调环境」）。

### 第三步：代码质量层走查

对被测模块源码做静态走查，按五类问题清单逐项过（详见 `references/edge-cases.md`）：

1. **响应性**：异步回调里是否丢响应性（如 `message: t('xx')` 未包箭头函数，语言切换后不更新）；
2. **边界**：空值 / 非法枚举 / 失败态 / 空选项是否都有兜底而非抛错；
3. **权限**：按钮显隐是否绑定权限码，与 spec 一致；
4. **竞态与时序**：连续点击是否防重、切换主体是否串号、卸载后回调是否置空；
5. **魔法值与规范**：硬编码字面量、非箭头函数、缺失类型标注等项目规范项。

产出 **R 级问题清单**：每条含 `文件:行号 / 问题描述 / 严重级别 / 修复建议`。

### 第四步：修复、回归与报告

1. **发现问题即修复**：R 级问题中能当场修的当场修（遵循项目编码规范），修完**回归对应断言**确认通过。
2. **无法当场修的**：标注遗留原因，写进报告遗留区。
3. **输出测试报告**（结构见 `references/testcase-template.md`）：
   - 报告路径固定为**当前项目根目录下的 `tests/report/<YYYYMMDD>/`**（例：`tests/report/20260921/测试报告.md`）；目录不存在则新建，同一天多次测试可追加日期后缀（如 `20260921-2`）或同名覆盖，按需选择。
   - 断言通过率（通过 / 失败 / 无法验证 各多少条）；
   - R 级问题清单及处置结果；
   - 覆盖缺口（哪些 spec 场景没测到、为什么）；
   - 证据（关键断言的 DOM / 网络请求摘录，截图接口超时时用 evaluate_script 读 computed style 代替）。

## 可选：生成单测文件

用户明确要求（「生成单测」「补测试文件」）或项目已有 Vitest/Jest 时：

1. 优先把「纯函数 / 工具函数 / 状态逻辑」类断言转成单测（浏览器依赖强的 UI 断言不强行转）；
2. 单测文件放项目测试目录（无约定时建议 `tests/` 或与源文件同目录 `__tests__/`），命名 `<source>.test.ts`；
3. 项目无测试基建时，先向用户确认是否补装（Vitest + 配置），不擅自改 package.json；
4. 生成后必须跑通：`pnpm test`（或项目对应命令）全绿才算交付，跑不通的单测不算完成。

### 测试路径决策（动 test 基建前先确认）

写测试前，先确认「项目允许测哪一层」，这是避免整轮返工的第一道闸门：

- **问清测试范围**：需要浏览器实测（chrome-devtools）、组件挂载（`@vue/test-utils` + vue 插件），还是纯逻辑单测（直接 import 函数）？三者对配置的要求差异很大。
- **确认 vitest 配置归属**：`vitest.config.ts` 是独立文件还是合并进 `vite.config.ts`？是否启用 `@vitejs/plugin-vue` / auto-import / components 插件？这些决定 `.vue` 能否被 import。
- **确认测试环境**：jsdom 还是 happy-dom；`include` 是否扫 `src/**`。
- **以现状为起点反向规划**：先跑一次 `pnpm test`（或最小 smoke test）验证当前配置能跑什么，再决定测试策略；不要按「理想配置」直接写满测试再撞配置墙。

### 纯函数抽取测试方案（当核心逻辑内联在组件里时）

当被测逻辑内联在 Vue 组件的 computed / methods 里、外部无法直接 import 时，有两种测试路径：

1. **挂载组件测试**：用 `@vue/test-utils` 挂载组件 + mock 全链路（api/pinia/i18n）。配置重、断言脆、依赖渲染细节，不推荐作为首选。
2. **抽取纯函数测试（推荐）**：把核心逻辑抽成纯（无副作用、纯输入→输出）函数，组件改为调用该函数，测试直接 import。

抽取流程：
- 确认被抽逻辑是纯函数（输入→输出，无副作用依赖 ref/reactive 之外的状态）
- **优先放进既有结构，不新建文件**：项目外层通常已有业务常量/工具文件（如 `src/views/<module>/constant.ts`），纯函数应并入该文件并保持既有导出风格；仅在确实无合适归属时新建 `.ts`。
- 组件的 `../..` 引用其他模块常量时，确认目标文件能被测试 import（不引 `@/constants` barrel，或 barrel 已在配置下可解析）
- 组件改为 `import` 并调用纯函数（行为不变，用 build + typecheck 验证）
- 测试文件 import 纯函数，直接断言

抽取约束：
- **属无行为变化的纯搬家**，不改变任何逻辑分支或返回值
- 抽取后必须跑 `pnpm test` + `pnpm typecheck` + `pnpm build` 确认无回归
- **若测试依赖把纯函数抽进既有文件后，该文件顶层依赖（如 `@/constants` barrel）会让测试无法加载**，优先把 barrel 引用改成叶子文件引用（`@/constants/common` 而非 `@/constants`），而不是再新建一个文件来绕开

### Vitest 配置注意事项

- **vitest.config.ts 独立 vs 合并 vite.config.ts**：独立文件启动快（~1.6s），合并进 vite.config.ts 会加载全部 vite 插件（~18s，慢 10 倍）。推荐独立文件。
- **vitest.config.ts 加入 .gitignore**：若项目不希望测试基建入库，把 `vitest.config.ts` 和 `tests/*` 加入 .gitignore。
- **`@` 别名**：vitest.config.ts 需单独配置 `resolve.alias`（或复用 vite.config.ts 已有的），否则 import `@/` 会失败。

### 测试文件维护

- **生产代码文件改名/移动时，必须同步更新测试文件的 import 路径**。遗漏会导致 `pnpm test` 跑红（模块找不到）。改名后立即跑一次 `pnpm test` 确认。
- 测试文件命名与被测文件保持可追溯关系（如 `commonTools.ts` → `commonTools.test.ts`）。
- **测试脚手架随配置变化及时清理**：调试期产生的一次性文件（`_debug*.test.ts`、dump 的 html/txt、临时 `setup.ts`）用完即删；配置改版后不再被引用的辅助文件（如 setupFiles 已移除仍留 `tests/setup.ts`）应一并删除，避免误导后人。
- **测试报告是必交付项**：跑完测试必须落地报告到 `tests/report/<YYYYMMDD>/`，只报结论不出报告视为未完成。

## 靠谱性自检（AI 生成测试的判断标准）

每次产出测试后过一遍（详见 `references/test-methodology.md` 第 3 节）：

- **断言可证伪**：每条断言都能明确说出「怎样算失败」；
- **正反都有**：至少一半用例覆盖「不应该发生」的行为；
- **不依赖实现细节**：断言描述外部可观察行为，不绑函数名 / switch 写法；
- **mock 不越界**：mock 只替代「不可控外部依赖」（后端数据），不 mock 被测行为本身；
- **变异抽查**：对关键断言做一次变异验证（临时改坏代码看测试能否抓住），抓住才算有效断言。
  标准操作步骤：
  1. 选一条核心断言（如地区拆分配对的 `Math.min` 取短逻辑）。
  2. 临时改坏被测代码（如 `Math.min` → `Math.max`）。
  3. 跑 `pnpm test`，确认对应用例**失败**（抓住变异）。
  4. 还原代码，重跑 `pnpm test` 确认**全绿**。
  5. 记录变异点与被抓住的用例编号到测试报告。
  若变异后测试仍全绿 → 断言无效，需加强测试用例。

## 硬约束（禁止事项）

- 不修改 openspec 产出物（proposal / spec / tasks）。
- 测试中发现的 bug 修复遵循项目编码规范（箭头函数、显式类型、注释规范等），修复范围仅限 bug 本身，不扩大重构。
- 未提交改动多时做变异测试，用「临时 commit → 变异 → 测试 → revert」，**禁止 git stash**（会与工作区冲突）。
- chrome-devtools 截图接口超时时，不反复重试，改用 `evaluate_script` 读 computed style / DOM 结构做证据。
- 真实联调才能验证的链路（后端就绪、loading 防重、成功刷新），如实标注「无法验证」，禁止宣称全覆盖。
