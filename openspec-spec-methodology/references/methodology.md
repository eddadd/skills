# OpenSpec spec 增强方法论详解

本文件是 `openspec-spec-methodology` skill 的方法论主体，供模型在触发本 skill 时完整理解并执行三大支柱。核心目标：**在 openspec 生成产出物之前，把需求质量提升到「AI 依 spec 实现不跑偏」的可验证水平**，产出物仍由 openspec 原样生成。

---

## 一、复杂需求拆解

### 1.1 拆解层级

把原始需求强制拆为四层，任何一层缺失都视为拆解不完整：

| 层级 | 含义 | 拆解产物 |
| ---- | ---- | -------- |
| 能力层 | 本次变更提供什么能力边界（做什么 / 不做什么） | 能力列表 + 明确的「不做」清单 |
| 需求层 | 每个能力分解为可独立验收的需求条目 | Requirement |
| 场景层 | 每条需求分解为行为化的场景 | `#### 场景` 矩阵 |
| 边界层 | 每个场景下的边界分支 | 独立场景条目（见支柱三） |

### 1.2 强制识别三种隐性需求

拆解时不能只做「正向翻译」，必须主动挖出三种容易遗漏的隐性需求：

1. **逆向约束（禁止什么）**：需求说「新增详情页」→ 隐含「侧边栏禁止出现入口」「列表页跳转后禁止再弹抽屉」。这类必须显式写成 `禁止` / `必须不` 形式的场景。
2. **跨模块契约**：路由、query 参数、接口数据流、动态路由权限过滤、keepAlive 缓存、共享枚举常量。这类牵一发动全身，必须在影响分析里点名到具体文件。
3. **交互时序**：先做什么后做什么（如费率抽屉「先选业务线 → 再拉支付方式类型选项 → 业务线变更清空已选」），时序错乱是 AI 跑偏的高发区。

### 1.3 决策点显式化

拆解中遇到的「二选一 / 多选一」决策（`path` 还是 `params`、骨架自请求还是组件自请求、哪种组件承载）必须：

- 在 proposal/design 中**显式声明选择**，并给一句理由（避免实现时自行裁决）；
- 一经选定，spec 中所有相关场景统一约束，禁止前后矛盾。

### 1.4 字段关联性显式化

当新增多个表单字段或接口参数时，必须显式声明字段间的关联/独立关系：

- **关联字段**：A 变化时 B 必须跟着变（如选通道→重拉支付方式、切业务线→清手续费币种）。逐一列出「A→B」联动对，写进 spec 场景与 design 决策。
- **独立字段**：A 变化时 B 不受影响（如手续费币种与通道无关）。逐一列出「A 不影响 B」独立对，写进 design 决策，避免实现时误清空。
- **遗漏后果**：若关联性未在预检阶段识别，实现时极易把独立字段误纳入联动清空（本次「币种与通道无关」即因预检阶段未识别而返工一轮）。

### 1.5 字段取值形态与承载组件能力校验

新增字段若由某个既有组件承载（下拉框、日期选择器、开关等），必须在预检阶段核对两件事：**取值形态兼容性**（1.5.1）与**所需能力是否被组件支持**（1.5.2）。任一遗漏都会在实现时踩坑。

#### 1.5.1 取值形态 vs 组件入参类型

- **取值形态列**：字段是布尔值、数值枚举、字符串枚举、还是对象？下拉选项的 `value` 用哪种形态（布尔 `true/false`、数值 `1/0`、字符串码值）？
- **组件能力核对**：承载组件的绑定 prop 类型是否接受该形态？例如共享组件 `FsSelect` 的 `selectValue` 类型为 `String | Number | Array`（不含 `Boolean`），若计划「下拉 value 用布尔 `true/false`」会触发 Vue 的 Invalid-prop 告警。
- **口径决策显式化**：若形态不兼容，在预检阶段就声明二选一——①扩展共享组件类型（`Boolean` 加入类型数组，注意 Vue 的 Boolean casting 副作用）；②改变字段落库/提交形态（如「下拉传 `1/0`，提交时转布尔」）。选定后写进 design 决策，全篇统一。
- **遗漏后果**：曾因预检未核对「布尔 value vs `FsSelect` 类型」而由评审阶段补出 F1，最终改为「下拉传 `1/0`、提交转布尔」，避免运行时报错。

#### 1.5.2 所需能力 vs 组件是否支持

计划让某个共享组件承担一项功能时，必须先确认该组件**是否透传 / 是否提供**这项能力，不能假定「同族组件都一样」。典型：

- **插槽透传**：`fs-table` 只透传 `bodyCell` / `headerCell` 两个具名插槽，**不透传 `expandedRowRender`**；需要展开行时不能用 `fs-table`，必须直接用 `a-table`（其 `#expandedRowRender` 具名插槽即可激活展开）。
- **能力开关**：分页开关、展开行、虚拟滚动、可编辑单元格等，使用前逐一核对目标组件 props / slots 是否支持。
- **预检动作**：写下「用 X 组件实现 Y 能力」前，先定位该组件的 props/slots/透传清单（读组件源码或 `.d.ts`），确认能力存在再落笔。
- **遗漏后果**：曾因假定 `fs-table` 能透传展开行插槽，实现到一半才发现不支持，被迫把整个表格从 `fs-table` 换成 `a-table` 并重写展开区渲染（含从 `h()` 改模板插槽）。

### 1.6 同名字段多来源的一致性核对

同一业务字段若在**多个接口**返回（如列表接口与详情接口各自返回 `is_profit_merchant`），必须在预检阶段显式声明：

- **来源清单**：列出该字段出现的所有接口（列表 / 详情 / 导出等），以及前端消费点。
- **一致性口径**：声明「以哪个接口为准」或「前端不仲裁、靠回归核对」。若前端无法仲裁（两接口语义可能漂移），至少要在 tasks 里挂一条**跨接口一致性核对**任务，作为联调回归项，不做静默补偿。
- **判定口径归一化**：同一字段在多个消费点（列表列展示 / 按钮显隐 / props 传递）必须使用**同一判定口径**（如统一 `=== true`），避免一处 `Boolean(v)`、一处 `v == true` 造成行为不一致；归一化后边界（非布尔真值、缺失）自然被同一逻辑覆盖。
- **遗漏后果**：若不在预检声明，实现时会出现「列表显示是、详情却不给操作」的错位，且前端无从仲裁。

### 1.7 接口返回结构预检

除字段名外，每个接口的**返回结构形态**与**字段归属**也必须在预检阶段显式声明，否则实现时极易把字段放错接口、把结构理解反：

- **返回结构形态**：列出每个接口返回的是「分页对象（`records`+`total`）」「单对象」「数组」还是「无返回」。数组接口要写明「元素结构」。
- **字段全集归属**：当列表接口与详情接口字段高度重叠时，必须显式声明「哪组字段由哪个接口返回」——是「列表项仅摘要、详情返回全集」，还是「列表项已内嵌完整详情字段、详情接口另返回数组」？**禁止凭「列表该瘦、详情该全」的直觉反推契约。**
- **同名不同义**：同一名称的枚举在不同字段下语义可能不同（如 `PENDING` 在订阅状态=「处理中」、在扣款状态=「下单中」；「失败」取值订阅用 `FAILED`、扣款用 `FAIL`）。发现同名或近名枚举，逐一核对归属与取值，不做合并。
- **遗漏后果**：曾因把「扣款详情 12 字段」默认放在详情接口、列表只留 5 列，被用户纠正「列表的数据应该和之前详情的数据一样，这些都要有」；又因把详情接口理解成单对象、实为数组而返工 mock 与类型各一轮。

### 1.8 粘贴契约的字段归属核对

用户常直接**粘贴接口文档 / 枚举定义 / Java 枚举片段**作为需求输入。粘贴内容可能与字段实际归属不符（笔误、复制残留、命名重复），预检时必须核对而非照抄：

- **同名标注核对**：若同一份粘贴内容里多组枚举都被标注为同一字段名（如两组枚举都标 `payment_status`），必须按**语义**判断归属并向用户确认，禁止照抄标注。
- **语义与字段名不符**：若某组取值语义明显不属于其标注字段（如「订阅生效/订阅失败」显然不是「扣款状态」），主动指出并提问。
- **不猜**：字段归属属于业务契约，用户粘贴的标注有冲突时，先问再写进类型定义，防止错误契约污染 spec/设计/类型。

### 1.9 未点名控件默认文本

筛选 / 表单字段若未在需求里显式声明控件类型（下拉 / 日期 / 开关），**默认按文本输入框实现**，并在预检结论里显式列出「哪些字段是下拉（及选项来源）、哪些是日期、其余为文本」，作为可核对清单。

- **原因**：实现者容易把「枚举类字段」惯性做成下拉，但用户可能只要一个文本搜索框。
- **遗漏后果**：曾把 `channel_type` 由文本输入框误做成下拉（用户原文只说 `payment_type`/`status` 是下拉），实现后才纠正。

### 1.10 新建页面/详情页的要素默认值确认

新建列表页、详情页时，以下要素属于**用户可控项**，预检阶段应逐项确认默认值，避免实现后连续返工：

- **详情页**：是否用 `<a-card>` 承载、右上角是否放「返回」按钮（返回目标）、导出按钮位置（`extra` 插槽）与入参范围、列表是否分页、展开行数据结构。
- **列表页**：时间列位置（首列/末列）、操作列按钮、字段顺序。
- **导出**：入参是「仅主键」还是「带当前筛选条件」。
- **遗漏后果**：曾因上述要素未预检，实现后分多轮追加纠正（返回按钮、创建时间移到末列、详情列表去分页、导出全部按钮位置、展开行结构）。

## 二、颗粒度标准：AI 不跑偏的可验证阈值

### 2.1 组成式场景（Given-When-Then）

每条需求必须拆成独立场景，场景格式必须可验证：

- **当（Given）**：描述前置状态 / 输入条件，必须是可构造的（如「用户访问 `/wallet/merchantDetail`（不带 query）」）。
- **那么（Then）**：描述系统行为，必须是可观察的（渲染、跳转、请求、隐藏），禁止「正常处理」「合理展示」这类自评词。
- **并且（And）**：并列的行为结果，一条场景可叠加多条。

### 2.2 可量化验收点

每个验收点必须给出**可核对的量化标准**，而不是「能正常显示」：

- 可数：字段数量、区块数量、请求次数、枚举项数量、选项项数。
  - ✅「概览区展示 5 个字段（商户编号、商户状态、进件状态、申请人身份、审核意见）」
  - ✅「打开页面期间 `getMerchantDetailServer` 调用次数为 1」
- 可对照：同数据源新旧实现逐项比对（字段标签数量、顺序、展示值完全一致）。
- 可检索：全仓检索某符号无残留引用、某枚举未重复定义。
- 可观测：打开某页签时才发起某请求、切走再切回不重复请求、规格组件树某组件未挂载。

### 2.3 自我验收措辞禁令

以下措辞在 spec 中**禁止出现**，出现即视为颗粒度不足，必须改写成可验证描述：

`合理即可` · `正常展示` · `妥善处理` · `美观` · `友好提示` · `不报错`（需改为「不抛错且展示空内容」这类行为描述）· `视情况` · `尽量`

## 三、边界条件表达法

### 3.1 强制边界场景清单

每个需求模块在写 spec 时，以下边界必须**逐一过一遍**，凡适用即写成**独立 `#### 场景`**（禁止塞进正常路径当一句注释）：

| 类别 | 边界 | 场景措辞示例 |
| ---- | ---- | ------------ |
| 空值 | 字段 / 区块 / 数组缺省 | 值为 `null` / `undefined` / `''` 时展示 `--`；区块数据缺失时不渲染标题且不报错 |
| 非法值 | 枚举不在映射表 | 非法枚举值不导致报错，展示兜底文案 |
| 失败态 | 请求失败 / 接口报错 | 请求失败展示空数据提示，页面其余部分可交互 |
| 空选项 | 下拉接口返回空数组 | 下拉为空且页面不报错 |
| 时序 | 首次进入 / 切走切回 / 往返切换 | 未访问不请求、首次访问才挂载、已加载不重复请求 |
| 权限 | 动态路由过滤 / 无权限 / 隐藏路由未授权 | 后端未返回菜单项时路由不注册、直接访问走 404；新增 `hideInMenu` 详情路由时，预检阶段必须抛「后端菜单是否返回该路由 name」让用户选定放行方式（后端补权限 / 挂子路由复用父权限 / 加入临时白名单） |
| 串号 | 切换主体 / keepAlive 缓存 | 切换商户时数据不串号；未开缓存时切回重新请求 |

### 3.2 边界表达三原则

1. **独立场景化**：每个边界是独立 `#### 场景`，与正常路径并列，不嵌套在场景正文里。
2. **可触发前置**：边界场景的「当」必须描述如何构造该边界（带什么参数、什么状态、什么枚举值）。
3. **结果可观察**：边界的「那么」必须说明系统在该边界下如何表现（展示什么、请求不发、不报错、兜底文案）。

### 3.3 验收标准的边界挂载

- 每个区块/模块的验收标准**必须包含边界条目**，格式 `边界：<行为描述>`；
- 涉及接口调用次数的，把「N 次」写进验收标准；
- 所有边界验收标准也必须是可量化、可核对的。

### 3.4 产出物语言约束

- 全部产出物正文**必须使用中文书写**，包括 proposal / design / spec / tasks 的叙述、场景「当/那么/并且」、验收标准、任务描述。代码符号、接口路径、类型名、命令等**强制技术标识符**除外，可保留原文（如 `getMerchantDetailServer`、`/agent-admin/user/export`、`EXPORT_DATA_FLAG.User`）。
- 禁止英文叙述混入正文（如「export the data」「show loading」）；测试质检时产出物同时是测试用例生成的输入，混入英文会降低可读性。

### 3.5 验收标准面向测试消费

本 skill 产出物在实现后会被**测试 skill** 消费（测试 skill 依据验收标准生成测试用例）。因此验收标准必须：

- **可转断言**：每个验收点是一个可判定的布尔条件（`请求恰 1 次`、`按钮不渲染`、`入参不含 page`），而不是方向性描述（`应当能导出`）；
- **独立成条目**：验收点逐条列出（`- 验收标准：` 前缀），不揉进叙述段落，便于测试 skill 逐条转成用例；
- **不可依赖实现细节**：验收标准描述「外部可观察行为」（渲染/请求/文案/权限显隐、请求次数、入参内容），**禁止**把内部实现（`useExport` switch 具体写法、某个具体函数名）作为验收条件 —— 测试 skill 与实现解耦，实现方式变化不影响验收；
- **区分语言与场景**：spec 场景（`#### 场景`）约束行为，验收标准约束「如何验证」；两者同时存在，缺一不可。

> 术语约定：本方法论中「验收标准」= 对某能力行为的可验证断言集合，供实现检查与测试 skill 生成用例；测试 skill 应优先消费 tasks.md 的「验收标准」条目，并对照 spec 场景互补。
> 职责边界：本 skill **不做浏览器验证 / 端到端实测 / 测试用例生成**，只负责把验收标准写成可转断言的外部行为描述；实际验证由测试 skill（浏览器实测、XHR mock、单测）承担。

## 三补、openspec 兼容性预检

在产出物生成前，对既有主 spec 做一次格式兼容性扫描，避免归档时匹配失败：

### 3.6 主 spec 章节头格式校验

- openspec-cn 解析器只识别 `## Requirements` 或 `## 需求` 作为需求章节头；`## 新增需求`、`## 需求列表` 等变体**不被识别**。
- 预检时扫描本次变更涉及的既有主 spec（`openspec/specs/<capability>/spec.md`），确认章节头是否为 `## 需求`。
- 若发现不兼容章节头，在预检结论中标注「需修正主 spec 章节头」，修正后再进入产出物生成。
- **遗漏后果**：不兼容章节头在 `validate --strict` 时报 MODIFIED 匹配失败，但报错信息不会直接指出「章节头格式不对」，排查耗时显著（本次 1 小时）。

### 3.7 delta 标题格式校验

- MODIFIED / ADDED delta 中的需求标题必须与主 spec 的 `### 需求:<名称>` 格式完全一致（含中文冒号）。
- 禁止使用 `### Requirement: <名称>` 英文格式——openspec-cn 在归档合并时按标题精确匹配，英文标题会导致 delta 找不到目标需求。
- 预检时确认 delta 中的标题与主 spec 既有标题逐字一致。

## 四、执行流程（在 openspec 生成前）

本 skill 只做增强预检，不生成任何产出物。执行流程：

```
[检测到 openspec 提案/变更生成命令] → 自动触发本 skill（无需用户手动调用）
  1. 需求理解：把原始需求复述为能力/非目标两条线，向用户确认
  2. 支柱一：复杂需求拆解 → 产出拆解结论（能力、需求、隐性需求、决策点）
  3. 支柱二：颗粒度校准 → 为每个需求列出「可量化验收点」候选
  4. 支柱三：边界铺排 → 过一遍强制边界清单，产出边界场景候选
  5. 注入上下文：把 2/3/4 的结论作为「增强约束上下文」交给模型
```
