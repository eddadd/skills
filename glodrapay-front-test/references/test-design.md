# 测试用例设计方法（从验收标准推导用例）

本文件是 `SKILL.md` 第 3 步的展开，回答三个问题：**该推哪些用例？推够了没有？漏了哪个？**
前半是**方法**（怎么推），后半是**清单**（推完对照自检）。方法框架与项目无关，长期有效；具体用例内容仍以目标项目的规范与代码为准。

---

## 零、用例的四个来源（优先级从高到低）

写用例前先把这四处过一遍，来源比灵感可靠：

1. **验收标准 / 规格场景**（最高优先）：openspec 的 `tasks.md` 验收标准编号与 `specs/` 里的 `Scenario`。一条验收标准至少转成一条用例；spec 里每个 `WHEN ... THEN ...` 场景就是一条现成的用例。
2. **走查定位到的分支**：第 2 步走查时标记的"该盯哪几个分支"（判定/映射/兜底/竞态），每个分支至少一正一反。
3. **契约边界**：接口 `model.d.ts` 的字段类型与可空性、组件 `props` / `emits` 的声明、对外导出的纯函数签名。契约允许的每种取值都该有对应用例。
4. **项目既有的坑**：git log / 历史报告 / `docs/correction-rules.md` 里出现过的缺陷，回归必测。

---

## 一、从一段逻辑推导用例：四步法

对每个待测单元（函数 / 组件 / 一段判定逻辑），按顺序做四件事：

### 第 1 步：划等价类

把输入空间切成"行为相同"的若干类，每类取一个代表值。重点是**别忘了无效类**（非法输入往往才是缺陷所在地）。

| 类型 | 含义 | 例（状态值判定） |
| --- | --- | --- |
| 有效类 | 合法且应正常处理 | `status = 'ENABLED'` |
| 有效边界类 | 合法但临界 | 空字符串合法时的 `''` |
| 无效类 | 非法，应有兜底 | `status = undefined` / `null` / `'UNKNOWN'` / `123` |

> 目标项目若在规范里规定了枚举/常量的合法取值，**以规范为准**，不要自己编取值。

### 第 2 步：找边界值

对每个**有界**输入，取边界及其两侧：

- 数值：`min-1, min, min+1, max-1, max, max+1`
- 长度：`0, 1, len-1, len, len+1`
- 数组：`[]`（空）、`[x]`（单元素）、`[x, y]`（多元素）
- 分页/索引：`page=1`、末页、越界页
- 日期/区间：起止同日、跨月、跨年、倒序区间

无界输入跳过边界，但**必须补"无界但异常的极端值"**（如超大数、超长字符串）看是否崩。

### 第 3 步：数分支（判定覆盖清单）

对被测代码**逐行扫一遍**，每个条件分支都要有能走到它的用例。用下面这张清单对照（这是本文件最实用的部分）：

| 结构 | 至少要有的用例 |
| --- | --- |
| `if (cond)` | cond 真、cond 假 |
| `if / else if / ... / else` 链 | 每个分支各 1 条 + 全部落空走 else 1 条 |
| `switch (x)` | 每个 `case` 各 1 条 + `default` 1 条（无 default 也要测"未列举值"） |
| `cond ? a : b` | cond 真、假 |
| `a && b` / `a \|\| b` | 短路两侧：`a` 假时 `b` 是否被求值（有副作用时必测） |
| `a ?? b` / `a \|\| 默认值` | `a` 有值（不走默认）、`a` 为 `null/undefined/0/''`（走默认，注意 `??` 与 `\|\|` 对 `0`/`''` 的差异） |
| 早返回 guard（`if (bad) return`） | 命中 guard（提前返回）、未命中（继续执行） |
| 循环 | 0 次、1 次、多次（循环体含状态累积或索引时必测） |
| `try / catch` | 正常路径、抛错路径（catch 是否真的兜住、finally 是否执行） |
| 可选链 `a?.b` | `a` 存在、`a` 为 `null/undefined` |
| 默认参数 `f(x = d)` | 传值、传 `undefined`（走默认）；传 `null` 是否也走默认视实现而定 |
| 异步 `await` | resolve、reject、pending（未 settle 时的中间态展示） |

### 第 4 步：补组合与状态

单条件的用例覆盖后，再看**组合与状态迁移**（缺陷常藏在组合里）：

- **判定表**：多个条件互相影响时（如"角色 × 状态 × 是否本人"），列出条件组合表，每行一条用例。组合爆炸时用**成对覆盖**（两两组合）折中，不要只测 all-true / all-false 两个极端。
- **状态机**：组件/流程有明确状态（如 `idle → loading → success/error`）时，**每个状态至少一条用例 + 每条合法迁移至少一条**；非法迁移（如 error 态点提交）也要有兜底用例。
- **时序/竞态**：快速连续操作（连点、快速切筛选）、请求乱序返回（后发的先回）是否有覆盖；用受控 Promise / fake timers 构造。
- **幂等与重复**：同一操作执行两次的副作用（是否重复提交、重复追加）。

## 二、先列清单，再写代码

**不要边想边写测试代码**——先在纸上（或对话里）列出用例清单表，再逐条落地。清单表就是第 3 步"同步记录每条断言对应哪条验收标准"的载体：

```markdown
| 用例编号 | 输入 / 前置 | 期望结果 | 依据（验收标准 / 分支 / 契约） | 类型 |
| --- | --- | --- | --- | --- |
| R-03 | status = undefined | 回落为默认态，不崩 | 契约：status 可空 | 反向/兜底 |
```

清单列完后，用下面的停止准则自检**漏没漏**，再开始写 `.test.ts`。

---

## 三、停止准则（"写够了"的判据）

一条被测逻辑**同时**满足以下条件才算写够：

1. 它涉及的**每条验收标准**都有至少一条用例，且能在覆盖矩阵里指认（见 `report-template.md` 的覆盖矩阵）。
2. 判定覆盖清单（本文第 1 节第 3 步）里，**每个分支结构都被命中过**——即"把该分支的走向反过来，至少会有一条用例转红"。
3. 每个**契约可空字段**都有"传入非法/空值"的兜底用例。
4. 走查标记的分支（R2 项）都有对应用例：发现的健壮性缺陷要先有用例**固化现状**（红或按预期绿），修复后转正向断言。

达不到就继续补；**补不完的（需要真实后端/浏览器/权限环境）记入"遗留事项"，不要用一条弱用例冒充覆盖。**

> **够用即停**：CPU 时间与上下文也是成本——四条判据同时满足就停手，不为了"覆盖率好看"继续堆用例，
> 更不要每加一条就重跑一次全量（见 `SKILL.md` 第 4 节执行成本控制）。

## 四、反模式（出现即返工）

- **只测 happy path**：正向全绿、反向全无，等于没测判定逻辑。
- **断言实现细节**：断言私有方法被调用、内部中间变量，而非用户可感知结果——重构即碎，且测不出真缺陷。
- **期望值与实现同源**：用例里直接复制实现里的映射表当期望（`expect(f(x)).toBe(sameTable[x])`），实现改错它跟着错，永远绿。期望值要来自**验收标准 / 契约 / 手算**，不是来自被测代码。
- **快照当覆盖**：`toMatchSnapshot()` 一把梭，看着覆盖了，实际不校验语义，且改坏了容易顺手更新快照。
- **断言写不出证据**：`expect(true).toBe(true)`、只断言"不抛错"。每条断言要能写成有意义的 `expect` 表达式。
- **用 `disabled`/`pointer-events` 拦截的分支当"已覆盖"**：这类分支在 jsdom 里点不动，测的是"点不动"而非"守卫逻辑"，见 `mount-testing.md` 踩坑 3。
- **为了全绿改断言**：失败先判根因（测试错 / 真缺陷），不得改断言迁就实现。

## 五、与报告的关系

- 本文件产出的**用例清单表**直接成为报告的"断言结果明细"（`report-template.md` 第 2 节）。
- 第 1 节"来源"与"依据"列，汇总成报告的"验收标准 → 用例覆盖矩阵"（`report-template.md` 第 2 节之后）。
- 停止准则第 3 条的自检结果，决定报告里"遗留事项"写哪些。
