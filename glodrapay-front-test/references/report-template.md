# 测试报告模板（tests/report/<YYYYMMDD>/测试报告.md）

按以下五段结构生成，全部中文（以目标项目 AGENTS.md 的语言要求为准）。文件头为 `# <变更名> 测试报告`。
**模板里的示例值都要替换成本次探测/执行的实际情况**，不得照抄占位内容。

## 文档头（元信息列表）

```markdown
# <change-name> 测试报告

- 日期：<YYYY-MM-DD>
- 被测对象：<变更名 / 模块 / 文件（中文说明）>
- 测试环境：<框架与版本 + 运行环境 + 是否具备组件挂载能力；如 "vitest 单测（jsdom，@vitejs/plugin-vue 混合模式；纯逻辑 + 挂载）">
- 依据：<openspec tasks.md 验收标准编号 + specs 场景；无 openspec 时写用户描述或"无">
- 测试文件：<本次新增/改动的测试文件相对路径列表>
```

**"测试环境"栏必须写第 1 步探测的真实结果**（框架 / 环境 / 挂载能力 / 包管理器）。项目无测试框架时写"无测试框架，结论基于走查证据（自动断言 0 条）"。

## 1. 结论摘要

- 断言通过率：**通过 X / 失败 Y / 无法验证 Z**（共 N 条自动断言；如有走查断言另注明 A 系列）
- R 级问题：**R1 a 个、R2 b 个、R3 c 个**
- 覆盖缺口：一句话概括哪些需浏览器实测/联调（详见第 4 节）

如有用户纠正或被测重构，在摘要后加 `> 说明：` 引用块注明。无测试框架降级时，此处必须明写降级及原因。

## 2. 断言结果明细

表格，每行必有证据：

```markdown
| 编号 | 断言 | 结果 | 证据 |
| --- | --- | --- | --- |
| C-01 | <常量/取值类断言> | 通过 | expect(...) 表达式 |
| T-01 | <正向/行为用例> | 通过 | expect(...) 表达式 |
| R-01 | <反向/兜底用例> | 通过 | expect(...) 表达式 |
```

编号约定：C=常量/取值，Q=查询/转换/接口，T=文案/展示/交互行为，R=角色/权限/兜底，A=走查断言。
走查可达但无法自动测的断言，结果列写"走查通过"或"无法验证"，证据列写走查证据（源码位置 + grep 结果等）。
无法验证的断言记"无法验证"，**不得标"通过"**。

### 验收标准 → 用例覆盖矩阵

紧接明细表，**每条验收标准一行的反向映射**，用来暴露漏测：

```markdown
| 验收标准 | 用例编号 | 覆盖判定 |
| --- | --- | --- |
| <tasks.md 1.6> | T-01, R-03 | 已覆盖 |
| <tasks.md 3.5> | — | **未覆盖**（原因：需真实后端联调，见第 4 节） |
```

被测对象无 openspec 依据时，改用"用户描述的验收点"逐条列出。**没有对应用例的验收标准必须显式标"未覆盖"并给原因，不许略过**。

## 3. R 级问题清单

```markdown
| 级别 | 位置 | 问题 | 处置 |
| --- | --- | --- | --- |
```

R1=功能错误，R2=健壮性缺陷，R3=规范违反（**须引用目标项目 AGENTS.md / docs 的规范原文**）。无问题时写"无"。已随用户纠正解决的问题，处置列写"已随纠正解决"并简述。

## 4. 遗留事项

- 需浏览器实测/联调的运行时场景，逐条列出（含场景编号）并说明为什么在当前环境无法验证
- 记录路径/规范类决策（如报告路径变更、引入测试框架的约定）供后续会话继承

## 5. 变异抽查记录

**关键分支必做**（纯走查、无自动断言的降级模式除外，此时写"未执行"并说明关键分支已由走查证据覆盖）。

- 执行时：列出被变异的分支、变异手法（反转 / 删除）、变异后测试是否失败。**失败 = 用例有效**；仍全绿 = 用例是假的，须补强或判定为"等价变异"（如实写明为什么该变异点物理不可达/行为无差异，见 `mount-testing.md` 踩坑 3）。
- 记录**还原实现并重跑全绿**的确认结果（防止交付的 src 与测试对不上）。
- 变异抽查是用例"真实性"的自检——判断关键分支的断言是不是空的。这一节空着，等于宣称用例有效却没有自证。
